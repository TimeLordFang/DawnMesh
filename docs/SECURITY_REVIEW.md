# Android 源码安全审查（2026-09-07）

## 结论和范围

在检查的 Android Flutter 主线、Dart 会话/传输/更新逻辑、原生音频/BLE/Wi-Fi 插件、C++ 核心和构建配置中，**未发现明确的恶意后门证据**（例如隐蔽上传录音、命令执行、动态下载执行代码、固定远程控制端）。这不是“已证明没有后门”：未取得你手机上的 APK，未做 APK 与源码一致性验证、全依赖源码/二进制逆向、动态抓包和模糊测试，也未全面审计其他平台。旧根目录 app/ 仅做相关构建、安全和蓝牙路径抽查。

原版不能按“默认端到端加密、安全匿名通话”理解。DawnMesh 已将随机邀请码组密钥加密接入全部应用入口；这修复默认明文和无邀请码入房，但并不提供每位成员的独立身份认证。

以下路径均相对于原 sunsetripple 仓库；可对照同路径的 DawnMesh 修复。

## 发现

## 联网、权限与数据路径

- 主线外网 HTTP 入口是用户在关于页面触发的 GitHub Releases 更新检查；本次未发现偷偷向分析/广告服务器上报的主线代码。DawnMesh 移除此入口的联网逻辑。
- `INTERNET` 同时用于本地 TCP/UDP，不能因应用“离线”就移除此权限，也不能仅凭该权限认定有后门。
- 录音由进房后的音频初始化开启，PTT 松手时 Dart 阻止语音帧发送；麦克风采集本身可仍保持打开。前台服务显示通知，START_NOT_STICKY，不见开机自启动/隐藏录音上传逻辑。后台/快速进退房仍需真机验证。
- Manifest 对外导出的主入口是 Launcher Activity；通话 Service 不导出。Flutter 主线不申请联系人、短信、通话记录、无障碍或安装 APK 的权限。
- 语音和聊天主要在内存处理，没有发现主线主动保存录音文件；日志、系统备份、进程内存及参与者自行录音意味着不能承诺绝对“无痕”。
- 旧 Kotlin `app/` 有 Google Nearby 依赖及另一套更新实现，不能把它的依赖/安全行为套到当前 Flutter APK；DawnMesh 不包含这套工程。

## DawnMesh 邀请码加密的边界

- 邀请码每次建房取 16 字节安全随机数，编码为 22 位 base64url；它不是用户自选短密码。使用域分隔 SHA-256 派生 256 位 AES 密钥，实际秘密熵为 128 位。系统不上传邀请码，也不把它写入日志或持久化设置。
- AEAD 使用 12 字节 nonce：每个发送器 8 字节随机前缀和 4 字节递增计数器，计数耗尽即停止加密。按发送器维护 1024 帧滑动重放窗口，旧于窗口的计数永远拒绝，认证失败不修改窗口；最多 128 个发送器前缀，达到上限需新建房。接收与发送按序处理。
- 新客户端必须收到包含本次 16 字节随机会话令牌的加密 admission，随后才能接受名单。录制的旧名单无法让一个新会话假入房。邀请码不符、密文篡改、重复帧、明文降级均在测试中拒绝。
- 这是一把共享组密钥。房主及所有持码成员均能解密所有内容、伪造组内身份；没有独立成员签名、前向保密或退房自动换钥。获取邀请码后也可能解密使用该码时录制的密文。要撤销已分享的邀请码，应结束房间再建房。
- 房间名、设备地址、人数、外层 senderId/序号及流量时序没有隐藏；参与者仍能录音/截屏，剪贴板中的邀请码取决于设备环境。加密不能提供匿名性或保证“无痕”。
- 未认证的连接仍可以消耗物理连接名额，传输层可能中继随后被会话层拒绝的密文。持码恶意成员、射频干扰、流量洪泛以及 TCP 慢接收者的资源压力没有在此次全部解决。

## 后续优先级

1. 每连接独立认证、成员号与认证链路绑定、入站验证后中继、房主端未认证连接期限、退出换钥。
2. TCP 背压和全链路速率限制；如果恢复 UDP 语音，必须加入 AEAD 与认证端点绑定。
3. 依赖清单/漏洞扫描、最终 APK 抓包、两品牌真机和多成员压力测试。本次源码审查不等于完成依赖二进制审计。

本次验证的是代码、协议测试和 APK 构建，不将未执行的手机测试或未解决的组内信任问题描述为已完成。

## 阶段 A 的实际修改

- iOS 普通 Wi-Fi 房与融合房分别通过 `_dawnmesh._tcp` / `_dawnfusion._tcp` 使用 Network.framework 点对点发现。浏览器、监听器按实例管理，防止关闭一个页面停止另一个房间的发布。
- 融合链路使用不透明 Apple endpoint 建立回环代理；保留 Bonjour endpoint 的接口作用域，不把广播中的 `127.0.0.1` 当作远端手机地址。关闭浏览不销毁已经建立的代理；退房、取消和迟到的连接结果释放资源。
- 本地和服务器目录继续按房间 ID 合并，区分“苹果点对点”来源；不同 Apple endpoint 不再因同为回环地址而被错误合并。
- 优先尝试本地路由，同时在 600 ms 后允许服务器备用路由参与。即使本地 WebSocket 已打开但邀请码认证没有响应，公网链路仍能接续认证；不能把 TCP 连通算作入房成功。
- 新链路需要重试时采用独立 PAKE 挑战标识，忽略旧回复；成员的稳定身份不变，保持既有包格式、房间认证与去重兼容。
- 服务器目录使用现有 API；无需本轮重写或部署服务端。服务器房间仍需所选服务器可达、授权有效及房间同步新鲜，双方均离线时不能经服务器发现。

## 真机验收入口

1. 正式 iOS 应用：17 Pro 和 XR 断开共同 AP、关闭蜂窝数据，Wi-Fi / 蓝牙开关保持开启，在前台创建/发现融合房，验证邀请码入房、双向聊天、通话、快速切页与重连；交换房主角色。
2. 正式跨平台应用：分别使用不同网络，选择同一个可达服务器，确认目录能显示同一房间并经邀请码入房；人为使本地候选无法完成认证时确认服务器能兜底。记录明确错误状态，不把服务器来源视作物理附近。
3. [安装 Nearby 原型并执行设备矩阵](../experiments/nearby/README.md)。免费 Apple 账号先用默认 Debug；有匹配热点能力的 profile 后再测 HotspotDebug。

这些结果决定阶段 B/C 是优先采用 Nearby 适配器，还是继续自有 BLE 引导与 Android 供网。无论选哪种方案，都需要保留已有身份、认证、媒体和服务器兼容，不能用原型配对替代正式房间准入。


## Nearby 0.1.0 真机反馈与 0.1.1 迭代

用户实测 iPhone 17 Pro（默认 Debug）、小米 15、一加 15T，断开共同 Wi-Fi，蜂窝保持开启：

- iOS 发布 → Android 发现、配对和双向完整性通过：32 KiB 往返 7502 ms，最大 RTT 405 ms，往返有效率 8.5 KiB/s。
- Android 发布 → iOS 未发现；尚未定位是广播介质、SDK 行为或扫描兼容问题。
- Android ↔ Android 能发现和首次传输，约 120+ KiB/s；再次测试报告传输失败，重发/发现后出现缺少数值状态码的 ApiException，杀进程后恢复。
- 正式 Android 的原有 Wi-Fi Direct 仍可使用。后续继续保留，不以 Nearby 作为 Android 互联的必要条件。

默认 iOS 原型没有启用 WebRTC 或业务服务器中继，其允许介质仅为 BLE、LAN、AWDL（热点配置才另加 Wi-Fi Hotspot）。蜂窝开启不会为其增加公网承载适配器；仅凭有效率不能推断介质，当前尚未证明跨平台 Wi-Fi 升级。逐块回显的结果也不能直接作为单向链路带宽或多人语音容量。

0.1.1 根据源码发现的缺口实施：失败回调按本轮 payload / 随机测试标识 / 序号隔离；连接生命周期隔离；配对后停止扫描和广播；iOS 等待完整 SDK 端点状态清理后重启；Android 停止后错开重启并显示具体 API 状态码。增加 BLE-only 发布对照开关，验证 Android → iOS 的发现问题，**不把该开关标记为已解决真机反向发现**。

阶段 B/C 接入原则：统一逻辑房主身份与无线发布角色；可让 iOS 作为无线发布端而 Android 发起连接；保留 Android 原生 P2P、ApplePeer、同网及服务器路径。Nearby 只作为候选适配器。需要先通过重复传输、重复配对、反向发现和真实语音时延验收，再接入正式融合房。Wi-Fi 升级在不支持热点签名能力时保留手工入网路径。

上轮阶段 A 的 GitHub Android / iOS Actions 均已成功。0.1.1 的回归验证及真机复测流程见 [Nearby 说明](../experiments/nearby/README.md)。本次不修改正式应用版本，不发布正式 tag。

0.1.1 最终本地检查：Android Debug APK 构建通过，JVM 回归 5/5、Lint 0；Swift 传输回归通过，iOS Release 真机架构未签名构建通过。正式应用源码未改，沿用上轮已通过的检查。


## Nearby 0.1.1 复测失败与后续边界

用户再次确认：iOS 仍无法发现 Android；Android 可发现 iOS，但连接不久即断开；Android ↔ Android 约 30–40 KiB/s，重复配对/传输仍有失败。`quality is not a medium identifier` 是我们添加的普通质量事件说明，不是 SDK 错误或断开原因；0.1.2 已改为中文分类信息。

0.1.2 针对固定 Swift SDK 停止广播可能拆除 BLE 服务的风险，取消连接成功后的停止发布操作，保留发布/监听服务直至退房式清理；加入默认 BLE 基线/不切网模式、断开后旧端点清理、连接/空闲时间及一键复制诊断。该版本 Android 构建、5 项 JVM 回归、Lint 0、Swift 回归和 iOS Release 构建均通过。无线故障未宣称已修复，需结合两端断开日志复核。

执行边界调整：Nearby 暂不满足作为正式跨平台发现/承载的验收条件，保留为独立候选；阶段 B/C 不再以 Nearby 成功为唯一前提。正式方案继续沿用自有 BLE 的发现/受保护控制通道方向，保留 Android 原生 Wi-Fi Direct、iOS ApplePeer、同网和服务器目录/中继；网络升级仍需系统确认及实际能力校验。本轮未将实验引入正式应用，也未发布正式 tag。
